# 後端修改總表與後續規劃

依據使用者的 [Rust 桌面整合構想分享對話](https://chatgpt.com/share/6aab53cd-d848-83ee-8bc0-1cc54338ef92) 整理。
本文件的「建議」是後續設計草案，不代表桌面已經實作；0.3.0 的正式契約以 [WEB_INTEGRATION.md](WEB_INTEGRATION.md) 為準。

## 本次先做：登入、模型、版本、選字聊天

| 後端工作 | 本次需要 | 桌面行為 |
| --- | --- | --- |
| 固定 device／token 路由、瀏覽器確認頁 | 是 | 一次性登入、最長 30 天 Token |
| 固定 Chat Completions 路由 | 是 | Bearer Header、stream=false、文字往返 |
| 模型代號清單與 alias → 真實模型映射 | 是 | 顯示快速／品質等名稱，不提供模型文字輸入 |
| 最新／最低版本 JSON 與下載頁 | 是 | 過舊提示更新；初次檢查失敗暫時可用 |
| 選字、快捷鍵、草稿預填 | 不需新路由 | 本機複製 → 草稿 → 使用者明確確認送出 |
| 翻譯、摘要、潤飾 | 沿用聊天路由 | 將動作指示與選取文字組成一般 messages |

維持桌面輕量、後端集中管理模型與權限。新功能不要先塞進固定路由表之外的臨時 API，再依賴使用者手動修改網址。
對外的 model alias 是穩定合約；伺服器可以調整實際模型、路由或配額，而不更動桌面選單的 id。

## 下一階段：通知與待辦事件（未實作）

後端先建立「事件」資料模型，再決定推播方式。WebSocket 負責即時通知，REST 負責補查；只靠 WebSocket 會遺漏離線期間的事件。

建議事件資料：

```json
{
  "id": "evt_唯一識別碼",
  "type": "task.completed",
  "title": "摘要已完成",
  "summary": "可回到工作頁查看結果",
  "created_at": "2026-09-17T02:00:00Z",
  "expires_at": "2026-09-24T02:00:00Z",
  "resource_id": "task_123",
  "read_at": null
}
```

建議未來路由（**尚未定案、0.3.0 不呼叫**）：

| 路由 | 用途 |
| --- | --- |
| GET `/lm_server/api/desktop/events?after=<cursor>` | 依使用者權限補查、分頁；回傳 events 與 next_cursor |
| WebSocket `/lm_server/api/desktop/events/ws` | 訂閱該使用者可見的新事件或事件識別碼 |
| POST `/lm_server/api/desktop/events/{id}/read` | 冪等標記已讀，不等同完成事件指向的工作 |
| GET `/lm_server/api/desktop/tasks/{id}` | 補查長任務狀態及結果 |

- 資料庫保存事件、接收對象、權限、已讀、期限與游標。推播失敗不丟棄事件。
- 建議至少一次送達，以 id 去重；重連後先 REST 補查，再接續即時推播。游標不能只用本機時鐘。
- 已讀／已送達／工作已完成是不同狀態，端點語意需分開；已讀請求重複送出也應成功。
- WebSocket 連線需要驗證，避免把長效 Token 放 query string 或記錄到 access log；跨帳號與群組都要授權檢查。
- 通知只顯示必要摘要；詳細內容點開後再驗權限。不要在鎖定畫面或 toast 暴露完整郵件或敏感文件。
- 桌面通知不搶焦點；使用者點擊才開主視窗或工作詳情。通知開關、靜音、重連與錯誤狀態由使用者控制。
- HTTP 換成 HTTPS 不會自動解決 Token 權限問題；兩者分開處理。內網也應規劃 TLS 與撤銷機制。

桌面端未來需處理系統列生命週期、Windows toast 身分註冊、事件儲存、去重與補查。這次沒有加入背景推播或常駐服務。

## 後續：Classic Outlook 郵件輔助（未實作）

建議先做使用者主動觸發、唯讀的 Classic Outlook 整合。Outlook COM／Object Model 是桌面端工作，不由網站直接存取公司電腦。
New Outlook 不能直接當成相同的 COM 介面使用；需另確認公司帳號、Microsoft Graph／其他連接方式與租戶權限。

第一步先取得選定郵件的最少欄位，再決定是否需要全文：

- 主旨、寄件者、收件者／副本、收件時間、未讀狀態，以及本機可定位的郵件識別碼。
- 由使用者確認要傳送的範圍；不在背景掃描整個信箱，不預設傳附件。
- 第一輪分類可用「重要／需更多資訊／一般」，附原因和不確定處，避免把模型猜測當確定事實。
- 需要全文或同討論串上下文時，再向使用者取得許可；依權限、大小、附件類型與保留政策限制。
- 郵件內容是待分析資料，不是工具指令。內文要求洩漏密鑰、執行工具或更改規則時不得照做。

後端可先規劃結構化分類回應，包含 category、reason、needs_body、requested_context 與引用位置；
任何新的郵件上傳／分類 API 都需要獨立的資料契約、權限、保留期限與刪除機制，不沿用無限制通用工具入口。
不要把 Classic Outlook 的本機識別碼直接當成全公司通用或永久識別碼。

桌面 COM 建議在專屬 STA 執行緒工作，處理 Outlook 未啟動、物件失效、離線及權限錯誤，不阻塞 UI。
第一版不寄信、不刪信、不移動、不改已讀狀態。回覆草稿先讓人檢查；即使未來增加寄信，也必須另做明確確認。

## 之後：知識查詢、附件與較長工作（未實作）

- **RAG 與引用**：回應提供來源名稱、片段位置、可存取的連結／文件 id；後端查詢前與點開時都驗證權限。模型回答不可把沒有取回的資料假裝成引用。
- **附件與 OCR**：沿用網站既有能力時，先訂上傳大小、格式、掃描、內容抽取、保留期限、失敗與取消契約。桌面不會因選取一封信就自動上傳所有附件。
- **長任務**：伺服器回 task_id，狀態使用 queued／running／completed／failed／cancelled；提供補查、取消與重試語意。取消不保證撤銷已產生的外部效果。
- **工作草稿**：產生待辦、郵件回覆或文件改寫後先預覽。建立任務、寄信或回填其他系統需獨立確認。
- **複製與回填**：0.3.0 只提供複製回覆；未來若加入回貼原應用，需重新確認目標仍是原欄位，避免覆蓋錯誤視窗。
- **能力協商**：功能增加後可規劃 capabilities 回應，讓桌面依後端支援程度顯示功能；與版本門檻分開，不能拿能力標示代替授權。

## 建議推進順序

1. 公司實機驗證本次固定登入、alias 聊天、版本失敗暫用與強制更新。
2. 在瀏覽器、Word、Classic Outlook 各驗證選字擷取；先解決跨應用複製問題。
3. 後端建立事件資料、REST 補查與已讀，再加入 WebSocket 與桌面通知。
4. 使用者主動選定郵件的唯讀摘要／分類，先採最少資料，不自動改動郵件。
5. 最後再整合附件、RAG、長工作與需要確認的外部操作。
