# 0.8.20 詢問解析與文件讀取修正

## 模型詢問

`tool`、`ask_user`、`finish` 統一接受「說明文字＋單一完整 JSON」，說明保存在活動紀錄並顯示；不再只允許工具附說明。既有嚴格操作結構、64 KB 上限、多物件／未知操作拒絕、不完整 JSON 最多兩次修正不變。`finish` 仍須通過成果核對。

`ask_user` 結束本次執行並顯示「需要你的補充」，專案狀態為「等待你的補充」，使用者匯入文字後再送出訊息繼續；不讓原執行器常駐等候。不增加後端路由，仍為 `skills:false`。

## MSG 與 COM 錯誤

原始 MSG 的 handle 保持拒絕寫入／刪除。在同專案 `_AI_Output/.read_<識別碼>/source.msg` 建立獨立位元組副本，固定目錄與副本身分後才交給已開啟的 Classic Outlook。副本允許 Outlook 開檔所需的讀写共享，不分享刪除；原件保護不變。不開啟 Shell、不枚舉信箱、不讀附件。

讀取後僅刪除本次暫存檔與空目錄，不遞迴清除未知內容。若 Outlook 暫留檔案 handle，正文已取得時仍回傳成功，另附清理提醒與目錄；不重讀、不誤報全文失敗。暫存目錄不視為交付成果，使用者可在關閉信件後清除。

Office／Outlook IDispatch.Invoke 保留 EXCEPINFO description、內層 scode／wCode，處理延後填入並釋放 BSTR。說明去除控制字元並限制 1200 字。外層 `0x80020009` 不能直接判定有對話框；現在可看到應用程式提供的原因。此修正針對開檔共享相容性與錯誤診斷，不保證可解密公司 MSG。

## PDF 現況

使用者確認公司為免費 Acrobat Reader，兩篇 PDF 可在 Reader 正常開啟，但 Word 開啟會亂碼。

本版仍在 AppContainer 用內嵌解析器處理 broker 讀到的資料。Adobe 能開啟不代表 LM_AI 能讀到相同解密內容；`invalid file header` 不能直接判定來源損壞。錯誤會引導模型使用 ask_user，請使用者由 Adobe 複製文字，再透過專案齒輪的「匯入文字」提供內容。

曾測試 Word 唯讀轉讀 PDF，但在本機有／無來源保護鎖兩種條件均未正常返回，因此未納入發行程式。**公司加密 PDF 的自動讀取尚未解決**；本版沒有新增 Adobe 自動化、OCR、任意指令或依賴。

## 交付範圍

0.8.20 EXE、簽署清單、原始碼與本機驗證紀錄；依 `Build.ps1 -EmptyCargoCache -TestOffice` 驗證 v142 x64、空 Cargo 快取與 --frozen。NSIS、歷史 ZIP 不重建。公司加密與實際 Outlook 結果仍需公司重測。

## 待評估：伺服器 PDF 轉 MD

使用者提出沿用伺服器轉檔，本版尚未實作。先以同一份公司 PDF 經現有一般附件流程驗證。附件目前上傳原始位元組，回覆 job_id、state、attachment_token 等資訊，桌面尚沒有取得完整轉換文字的欄位／介面。若伺服器可解析，後續需定義受驗證的轉換文字取回介面與來源版本對應，供專案 read_file 使用；MD 只作內部格式，不改變 TXT 成果偏好。若上傳的仍是不可解析密文，搬到伺服器轉檔本身不能解決。
