### 現況與問題假設

- `src/projects/context.rs`：目前報表標示8,000–12,000，估算超過12,000 tokens時逐組移出較早工具結果，最少保留最後一組。
- `src/projects/progress.rs`：每輪最多帶最近三組工具歷史，即使未超過token預算亦如此；自動整理在30組或156,000 bytes觸發，整理後只留兩組。另外有120,000／240,000 bytes的訊息縮減門檻。
- `src/projects/runner/execution.rs`：指定資料集匯出成功後立即整理，只留最後一組。
- 上述機制可能使剛讀取的原文經過少量操作就離開上下文，促成重讀循環；目前是程式檢視所得的原因假設，尚未以同一批真模型任務證明改善效果，不能只提高12,000常數就宣稱問題解決。

### 已確認的調整方向

1. 完整請求以50,000 tokens為軟目標，包含系統提示、技能、筆記、工具定義、工具結果與原文；不刻意填滿預算。沿用估算與API實際usage分開記錄的原則，仍遵守服務端能力與傳輸限制。
2. 取消日常「最近最多三組」的固定投影限制，預算內保留已讀原文及工具結果，不因多做幾次操作就移出。不得刪除使用者原始要求或補充，也不拆開工具呼叫與結果。
3. 超過50,000後才進行日常預算整理，整理至約40,000，避免每讀一頁就再次整理。優先移出較早且已完成階段的結果，保留目前仍在比較、引用或修改的原文及最新工具結果；實作時需以可核對狀態決定保留，不憑模型摘要假定工作完成。
4. 放寬固定操作次數與匯出成功後立即整理的規則，並同步檢查bytes門檻，避免較早觸發而抵銷50,000目標。錯誤恢復、使用者新指示及模型主動整理的用途分開評估，不一律放寬；不放寬無進展／失敗保護或重播成功操作。
5. 不增加新的筆記／摘要流程；既有技能、閱讀筆記、操作封存與去重機制維持。完整原文仍可按來源與操作ID查回，原文未隨請求送出不代表未讀或未執行。

### 驗收與比較方式

- 使用相同文件、要求、模型與可固定參數，比較調整前後的重複讀取次數、整理次數、完成步數、整個任務累計input tokens及成果完整性；估算值與API usage分開記錄，缺少usage不得推算為實測。
- 驗證未超過預算時超過三組的原文仍可保留、超標後整理有緩衝、最新結果／目前必要證據與使用者要求保留，以及工具呼叫／結果配對、來源版本、操作去重與續接不受破壞。
- 真模型文件閱讀、跨文件比較及多步匯出任務須觀察是否減少「讀取→整理→重讀」循環；單次輸入增加不代表整個任務用量增加或減少，均以實測比較，不預先宣稱改善。
- 此項與LTO的量測基準分開，避免功能行為變更干擾D02b同來源配置比較。0.9.9依最新指示只提交來源；合併到0.9.10後依專案規則完成v142 x64、空Cargo快取frozen及相關測試；必要封裝與真模型缺項如實記錄。未實測項目不得標示通過。
