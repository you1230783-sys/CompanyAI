# 0.8.22 專案筆記與有限續接

本版改善專案內模型回覆不穩，不改一般聊天、Outlook、PDF 轉換或 Office 操作方式。PDF 路由已獲使用者回報可閱讀，真實 GLM／Gemma 的續接品質仍待測試。

## 回覆解析與完成

- 說明文字＋唯一完整 JSON 繼續執行並顯示說明；JSON 字串內的括號不當成第二個物件。
- 多候選 JSON、自我修正產生的兩份 JSON、截斷／無法解析、空回覆、裸 done、action:done、空 finish.message 都要求修復，不執行任何候選操作。
- 沒有成果的裸「已完成／done／ok」不當成答案；正常短答案不以字數拒絕。「已完成」若附有效已儲存 artifacts 可交付。真正是否完成仍由模型判斷，桌面不宣稱驗證所有摘要內容正確。
- 未知工具仍停止。ask_user 等待使用者補充，不視為格式失敗。既有成果讀回／版本／所有副本檢查維持。
- 專案 POST／GET 分開檢查任務信封與模型正文；server completed 但 result 不可解析屬回覆修復，不無限輪詢同一空結果。任務 ID 不符、未知 server state、failed／cancelled 則停止。
- POST 結果未知先以原 client_request_id 查詢；仍無法確認便停止，不換 ID 重送。只有已確認本輪 completed 才發起下一輪模型修復。

## 短筆記

每三次帶來新區間的 read_file，或六次成功且不同結果的非瀏覽工具操作，下一輪附筆記要求。list_files、重複讀取、operation_id 重播與失敗不增加筆記計數。兩類計數任一達門檻即可；接受筆記後同時歸零。

筆記是可選同層字串，不新增工具，例如：

```json
{
  "action": "tool",
  "operation_id": "read_next",
  "request": {"tool": "read_file", "path": "paper.pdf", "offset": 18000},
  "progress_note": "已確認的累積重點、來源 path/revision/offset、未完成事項與下一步。"
}
```

建議 200–400 字，上限 2000 字。只記工作摘要，不要求思考過程；不為筆記額外呼叫模型，已能交付就 finish。太頻繁的筆記不更新檢查點；格式或大小錯誤要求修復。筆記只涵蓋該回覆之前已完成的工具，不能包含尚未執行的工具作為成功證據。

程式另保存來源版本、實際讀取區間聯集、第一個尚未讀取位置、copy_id／revision／saved_revision／paths 及工具結果摘要。跳讀尾段不會標示全文已讀。讀到來源新版本時撤銷舊筆記的精簡資格，重新保留原始證據。

## 續接與資源上限

- 同一段無有效進展最多修復兩次，全任務最多六次。第一次保留完整當前上下文，附限長錯誤回覆；第二次啟用筆記精簡，不附壞回覆。
- 原始使用者需求與補充訊息始終保留；有有效筆記才可省略其涵蓋的較早工具歷史。最近兩筆已摘要操作及全部未摘要結果仍保留。沒有筆記便不丟棄原文。
- 沿用同一個 broker、AppContainer worker、記憶體工作副本與 PDF 快取，不從任務起點重跑。相同 operation_id＋相同參數回傳快取結果；同 ID 不同參數拒絕。模型仍須依真實版本繼續，不以新 ID 重做寫入。
- 工具上限 60 次（包含重播）、模型回覆上限 80 次、連續八次無有效進展停止、整次 30 分鐘。修復不占工具次數，但占模型次數。
- 上下文原始內容超過 120,000 UTF-8 bytes 啟用精簡；組好後超過 240,000 bytes 停止，不靜默裁掉未摘要內容。這是 App 文字預算，並非模型 token 計算。
- 專案訊息最多 204 則、每則 64,000 bytes；一般聊天仍為 40 則。後端須支援實際送出的長度，不保證任意部署皆有相同模型上下文容量。
- 進度、筆記及請求沿用 DPAPI 任務紀錄；結束／停止會關閉 worker。重啟應用只恢復結果及中斷說明，不自動重播或恢復檔案授權。

## 網站與交付

沿用背景 Chat Completions、skills:false 和桌面自訂 Skill。progress_note 位於模型回覆 JSON 內；筆記要求與真實狀態位於 messages，不新增頂層 HTTP 欄位。無需新增路由。

交付 EXE、EXE 簽署清單、原始碼及文件；不重製 NSIS／ZIP。測試以真正 loopback HTTP、AppContainer、檔案讀回驗證，不能代替公司實際模型的摘要品質與速度測試。
